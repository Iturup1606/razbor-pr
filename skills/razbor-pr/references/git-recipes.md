# Как взять изменения и читать код: команды

Все команды обычные `git` и `gh`, без каналов (`|`), без here-doc и без bash-приёмов, поэтому одинаково работают в PowerShell, cmd, bash и zsh. Только чтение.

## 1. Общие правила для команд

- Пути в командах пиши с `/`, даже на Windows.
- Русские имена файлов: добавляй `-c core.quotepath=off` перед командой (`git -c core.quotepath=off diff ...`), иначе имена придут в кавычках с кодами.
- Аргументы с пробелами или фигурными скобками бери в двойные кавычки.
- `gh` с ключом `--json` печатает JSON; читай его глазами. Ключ `--jq` с кавычками внутри в Windows PowerShell 5.1 ломается, не используй его.
- Длинный вывод (большой дифф) читай кусками: сначала `--stat`, потом дифф по файлам.

## 2. PR по номеру или ссылке

Сводка (поля одной строкой, без пробелов после запятых):

```
gh pr view 123 --json number,title,state,body,baseRefName,headRefName,baseRefOid,headRefOid,mergeCommit,additions,deletions,changedFiles,files,commits,statusCheckRollup
```

Другой репозиторий: добавь `--repo владелец/имя`. Ссылку вида `https://github.com/владелец/имя/pull/123` можно передать вместо номера.

Дифф целиком и только список файлов:

```
gh pr diff 123
gh pr diff 123 --name-only
```

Состояние `state`:

- `OPEN`: «после» это `headRefOid`, «до» это `baseRefOid` (точнее, их общий предок: `git merge-base <base> <head>`, если оба коммита есть локально).
- `MERGED`: «после» это `mergeCommit.oid`. Если слияние было обычным или squash, «до» это его первый родитель `<oid>^1`. Если коммит слияния не найден локально, читай через `gh api` (раздел 6).

Статус проверок (CI) уже в поле `statusCheckRollup`. Красные проверки упомяни в первой же строке разбора.

## 3. Ветка

Основную ветку узнай: `git symbolic-ref refs/remotes/origin/HEAD` (если пусто, спроси или возьми `main`/`master`, что есть в `git branch -a`).

```
git merge-base main feature/x
git diff --stat main...feature/x
git diff main...feature/x
git log main..feature/x --format=%h%x20%an%x20%s
```

Три точки в `diff` означают «изменения ветки от места, где она отошла». Две точки тут не использовать: они покажут и чужие правки основной ветки.

Чужая ветка с сервера: `origin/feature/x`. Если её нет локально, это просьба к человеку (нужен `git fetch`), сам не делай.

## 4. Последние коммиты

```
git log -n 5 --format=%h%x20%an%x20%s
git diff --stat HEAD~3 HEAD
git diff HEAD~3 HEAD
```

Один коммит: `git show <хэш>`. Диапазон: `git diff <хэш1> <хэш2>`.

## 5. Неотправленные правки

```
git status --short
git diff
git diff --staged
```

Новые файлы без `git add` не попадают в `git diff`; прочитай их по списку из `git status --short`.

## 6. Читать файл «до» и «после»

Локально, если коммит есть:

```
git show <коммит>:путь/к/файлу
git ls-tree -r --name-only <коммит>
git ls-tree --name-only <коммит> путь/к/папке/
```

Если коммита нет локально, но PR на GitHub:

```
gh api "repos/{owner}/{repo}/contents/путь/к/файлу?ref=<хэш>" -H "Accept: application/vnd.github.raw"
```

`{owner}` и `{repo}` `gh` подставит сам из текущей папки, а при `--repo` укажи их явно. Чужой дифф с большим контекстом вокруг правок: `git diff -U15 <до> <после> -- путь/к/файлу`.

Номера строк в разборе называй по версии «после» и подписывай, если речь о «до».

**Как не запутаться в номерах.** Выбери один способ и держись его: либо смотри файл целиком в нужном коммите и считай по нему, либо бери номера из заголовков дифф (`@@ -77,6 +77,7 @@` значит, что кусок начинается с 77-й строки). Если вывод команды сохранился в файл уже с номерами, не открывай его снова инструментом, который добавляет свою нумерацию: номера удвоятся. Сомневаешься в номере, сверь с заголовком `@@` того же места в диффе.

## 7. Искать связанные места

```
git grep -n "имя_функции" <коммит>
git grep -n "имя_функции" <коммит> -- "*.py"
git grep -l "имя_функции" <коммит> -- "*test*"
```

Зачем: кто вызывает изменённое, где повторяется то же значение (константа, имя настройки, список допустимых значений), какие тесты упоминают это место. Поиск по именам делай всегда по обоим коммитам: то, что исчезло из «после», видно только в «до».

## 8. История и авторство

```
git log -n 5 --format=%h%x20%ad%x20%s --date=short -- путь/к/файлу
git blame -L 40,70 <коммит> -- путь/к/файлу
```

Зачем: узнать, почему строка появилась и кто на неё мог положиться. Сообщение коммита это подсказка, а не доказательство; его утверждения проверяй по коду.

## 9. Чего не делать

- `git checkout`, `git switch`, `git merge`, `git rebase`, `git reset`, `git stash`, `git pull`, `git commit`, `git push`, `git clean`, `git apply`.
- `gh pr checkout`, `gh pr merge`, `gh pr review`, `gh pr comment`, `gh api` с методами POST, PATCH, PUT, DELETE.
- Запускать тесты, сборку, установку пакетов или скрипты из репозитория: они пишут файлы и могут выполнять чужой код. Команду для запуска предложи человеку.

## 10. Что было после слияния, сгенерированные файлы и зеркала

**После слияния.** Если PR влит, посмотри, не чинили ли те же файлы позже:

```
git log <коммит слияния>..HEAD --format=%h%x20%s -- путь/к/файлу
```

Найденный коммит прочитай. Риск, который он закрыл, в разборе помечай «исправлено позже в <хэш>».

**Сгенерированный файл** (реестры, шпаргалки, замки зависимостей, сборки). Главный вопрос: правили его руками или пересобрали скриптом, и все ли изменения в нём объясняются правкой исходника.

```
git diff -U0 <до> <после> -- путь/к/файлу
```

Прочитай каждую изменившуюся строку. Строка, которую исходная правка не объясняет, это находка или как минимум строка в «не проверено» («файл пересобрали, и в него попало постороннее изменение»). Сравни слова описания PR («изменились только такие-то строки») с реальным дифф. Найди скрипт, который файл создаёт (`git grep -n "имя_файла" <после>`), и прочитай, откуда он берёт данные.

**Зеркало или копия** (файл, который должен совпадать с живым или исходным). Сравни содержимое с оригиналом любым средством чтения (например, `Compare-Object` на PowerShell, `diff` на macOS и Linux) после приведения переводов строк к одному виду. Результат запиши как факт: «совпадает» или «расходится в таких-то строках». Оригинал лежит вне репозитория, пометь «вне репозитория».

**Внешние файлы, которые читает код PR** (настройки, каталог установленных плагинов, живые конфиги). Читать можно, помечай «вне репозитория». Это данные на машине человека: переносить из них в разбор секреты и личное нельзя.
